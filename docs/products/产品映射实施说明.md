## 1. 要解决什么问题

评论导入后，带 `platform_sku` 的商品评论多数停在 `product_mapping_status=pending`，批次里会看到「待映射」。  
**业务心智：** 维护一张 **公司内部 SKU 主数据表**（品牌 / SPU / SKU / 中文名），与平台无关；同一产品在各平台共用同一 `internal_sku`。  
**技术落库：** 写入 BigQuery `dim_product_mapping`（字典里的「平台别名表」）；首期由系统在入库时自动补 `alias_type=seller_sku`、`alias_value=internal_sku`、全局作用域，**Excel 里不让业务填 platform / store / alias**。

**不要求**一次全部映射完；要求：

- 未映射诚实显示为 `pending`
- 已确认映射可验证
- 冲突进 `conflict`，不静默挑一条

## 3. 数据契约（必读摘要）



### 3.1 两层概念（业务表 vs 库表）


| 层                          | 是什么                                                               | 谁维护         |
| -------------------------- | ----------------------------------------------------------------- | ----------- |
| **内部 SKU 主数据**（Excel / UI） | `brand_key` + `internal_spu` + `internal_sku` + 中文名等；**全局、与平台无关** | 产品主数据负责人    |
| `dim_product_mapping`（BQ）  | 字典定义的物理表；首期一行对应一条内部 SKU，系统写入 alias/scope 技术字段                     | 导入 API 自动生成 |


字典 §7 要求表里有 `platform` / `country_code` / `alias_type` / `alias_value` 等，是为 **多平台、跨店 ASIN、同一 Seller SKU 多店铺** 等复杂场景预留的。  
**首期 Feimei 约定（与现有 653 行 H02 一致）：**

- 评论里的 `platform_sku` ≈ 公司统一货号，与 `internal_sku` 相同或可 1:1 匹配
- 匹配规则：`brand_key` + `platform_sku` → 主数据 `internal_sku`
- 入库 `dim_product_mapping` 时：`alias_type='seller_sku'`，`alias_value=internal_sku`，`platform/country_code/store_id` 用全局占位（如 `*` / 空），`product_scope_id` 由 `brand_key+internal_sku` 生成，`mapping_status=confirmed`
- **以后**若出现「同一 ASIN 多市场不同 SPU」等，再扩展 Excel 列或单独维护平台别名，不阻塞首期

库表其余字段：`mapping_version_id`、`mapping_publication_id`、`valid_from`、`mapping_method=master_data`、`source_reference` 等仍按 DDL 填。

### 3.1.1 BigQuery 要不要删字段？

**不要删** `dim_product_mapping` **的列。**


| 看法                             | 结论                                                                                               |
| ------------------------------ | ------------------------------------------------------------------------------------------------ |
| 模板没有 platform / alias，库表是不是多余？ | **否。** Excel = 业务输入面；BQ = 字典契约。技术列由导入 API **自动填占位值**，不是让人填                                       |
| 能否为了简单新建一张「只有 SKU 的窄表」？        | **不建议。** 会与字段字典、已有 DDL、后续扩平台冲突；首期用同一张表 + `global_sku_v1` 规则即可                                    |
| 哪些 Excel 列根本不进 BQ？             | 仅历史上的 `notes`（模板已去掉）。`shade_code` 可写入 `variant_name` 或暂不落库、只把 `shade_name` 写入 DDL 的 `shade_name` |


**必填技术列（Excel 没有 → 代码补）：**  
`mapping_version_id`、`mapping_publication_id`、`platform`、`country_code`、`product_scope_id`、`alias_type`、`alias_value`、`mapping_granularity`、`valid_from`、`mapping_status`、`mapping_method`、`mapping_rule_version`、`source_reference`  

**可空、首期常留空：**  
`marketplace_id`、`store_id`、`authorization_key`、`parent_product_id`、`platform_product_id`、`asin`、类目、`valid_to`、`mapping_confidence` 等  

**业务列直接落入同名 BQ 列：**  
`brand_key`、`internal_spu`、`internal_sku`、`product_name_cn`、`product_name_en`、`shade_name`、`source_reference`

### 3.2 评论投影（写在 `fact_review`，不改原文版本）

可更新字段：`product_mapping_status`、`mapping_version_id`、`mapping_rule_version`、`mapping_publication_id`、`mapping_updated_at`、`brand_key` / `brand_name`、`internal_spu` / `internal_sku`、`product_name_cn` / …、`product_granularity` 等。

规则：

- 重映射 = 新的 `mapping_publication_id` + before/after 可追溯；**不**改 `review_version_id` / 正文
- 只确认到 SPU 时，SKU 可空；不要伪造 SKU
- 多个可用别名指向不同内部产品 → `conflict`



### 3.3 匹配规则（首期）

1. 评论有 `platform_sku` → 用 `brand_key`（评论行或批次上下文）+ `platform_sku` 查主数据 `internal_sku`
2. 命中 → `product_mapping_status=confirmed`，写入 SPU/中文名等
3. 未命中 → `pending`
4. 同一 `brand_key+internal_sku` 重复定义且指向不同 SPU → `conflict`

字典里的「变体 → 店铺 SKU → ASIN → 产品级」顺序 **首期不实现**；仅当后续接入纯 ASIN、无统一 SKU 的平台导出时再启用。

## 5. 建议交付（本期 MVP）

按优先级，建议一次做完「能用」的闭环，不必一次做满方案理想态。

### P0 — 必须

1. **对照表导入 / 列表**
  - API：上传 Excel → 校验 → **展开技术字段** → 写入 `dim_product_mapping`（新 `mapping_publication_id`）
  - Web：映射页（列表 + 上传 + 下载模板）
  - 解析工作表 `01_内部SKU主数据`；兼容旧表 `01_产品SKU对照`（`alias_value`→`internal_sku`）
  - **再次导入 = 按 SKU 覆盖**（见 §6.1），不是只追加
  - 同一次 Excel 内：同一 `brand_key+internal_sku` 出现多行且 SPU/名称等不一致 → 拒绝或标 `conflict`，不静默取最后一行
2. **评论导入时自动匹配**（改 `import/service.ts` 逻辑，不是改表结构）
  - 写 `fact_review` 前查有效 `confirmed` 映射：`brand_key + platform_sku` = `brand_key + internal_sku`（即 `alias_value`）
  - 命中 → 填内部字段 + `product_mapping_status=confirmed`，**不计入** `unmapped_rows`
  - 未命中商品评论 → 仍 `pending`，计入 `unmapped`
  - 多命中冲突 → `conflict`（质量计数若有 `mapping_conflict_rows` 可一并更新）
3. **待映射清单**
  - 能查询：当前 `pending`/`conflict` 的 `(brand_key, platform_sku)` 及出现次数
  - 便于业务补主数据，而不是只看批次一个总数



### P1 — 强烈建议（仍属映射，不做媒体/部署）

1. **补映射后回写历史评论**
  新上传对照表后，按新 publication 重算命中的 `fact_review` 投影（append-only 或按字典允许的更新策略；至少能把旧 pending 变成 confirmed）。
2. **单条人工确认**
  待映射队列里选一行 → 填 SPU/SKU → 写入维表并触发回写。



### 明确不做

- 媒体下载 / Signed URL
- Cloud Run / Google 登录 / Firestore
- 差评分类、LLM、Embedding
- 完整 publication gate / 双 Job 并发验收证据（可沿用现有导入写库方式，映射写入保持简单可审计即可）

## 6. 首期实现约定（写代码时照此）

1. **Excel 解析**：只读 `01_内部SKU主数据`（或兼容旧表 `01_产品SKU对照`：`alias_value` → `internal_sku`）。
2. **写入 BQ 时自动补技术字段**（**不删 DDL 列**）：
  - `alias_type='seller_sku'`，`alias_value=internal_sku`，`platform_sku=internal_sku`（可追溯）  
  - `platform='*'`，`country_code='*'`，`store_id=NULL`（表示全局内部货号）  
  - `product_scope_id = sha256(canonicalJson({ brand_key, internal_sku }))`  
  - `mapping_rule_version='global_sku_v1'`  
  - `mapping_status='confirmed'`，`mapping_method='master_data'`  
  - `approved_by` / `approved_at`：上传人 + 上传时间（confirmed 条件字段）
3. **评论匹配**：`fact_review.brand_key` + `fact_review.platform_sku` = 主数据 `brand_key` + `internal_sku`（查 `alias_value` 或 `internal_sku` 均可，首期二者相同）。
4. **同文件内冲突**：同一 `brand_key+internal_sku` 两行指向不同 `internal_spu`（或其它关键属性不一致）→ 拒绝导入或标 `conflict`。
5. **valid_from**：上传时刻；`valid_to` 空。
6. **逻辑要改的地方**：新增 mapping 上传 API + 评论导入查表匹配；**不必**改 `base_tables.sql` 删列。若云端表已按旧 DDL 建好，保持原样即可。



### 6.1 再次导入：按 SKU 覆盖（业务约定）

SKU 对照表**不是**评论那种「同文件幂等、不同内容追加版本」；主数据以业务最新表为准。


| 场景                                                        | 行为                                                                                                             |
| --------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 第二次（或第 N 次）上传中的某行，库里已有相同 `brand_key` **+** `internal_sku` | **覆盖**：用新行的 SPU、中英文名、色号、粒度、`source_reference` 等更新该产品；生成新的 `mapping_version_id` / 纳入本次 `mapping_publication_id` |
| 上传中有库里没有的 SKU                                             | **新增**                                                                                                         |
| 库里已有、本次 Excel **未出现**的 SKU                                | **保留不动**（首期不做「全量同步删除」；避免一次漏导清空主数据）                                                                             |
| 覆盖后评论侧                                                    | 匹配键仍是 `brand_key+internal_sku`；名称/SPU 变更后，P1 回写历史评论投影；P0 至少保证**之后新导入的评论**读到最新主数据                               |


实现提示（二选一，文档不绑死）：

- **推荐首期**：对命中键先将旧行 `valid_to=本次上传时刻`（或 `mapping_status=invalid`），再插入新 confirmed 行（半开区间，符合字典有效期）；查询只取当前有效行。  
- 或：按 `brand_key+internal_sku`（及全局 `platform='*'`）做 MERGE/删后插，保证查询视图里每个 SKU 最多一条当前记录。

导入结果应回报：`新增 N` / `覆盖 M` / `跳过或失败 K`，便于业务确认。
