# 统一评论字段字典

> 内容版本：v1.1；修订日期：2026-09-05。为保持原有文件引用，文件名仍为《统一评论字段字典 v1.0.md》。
> 配套方案：V1.2。本文是字段名、类型、可v_review_curren空性、键和状态的唯一正式定义；方案只描述用途和流程。
> 状态：技术设计已统一，可据此生成本地 Schema/DDL 和开发模拟数据链路；真实平台字段映射仍须用样本验证。本次修订没有创建云端表或部署应用。

## 1. 统一命名与兼容

所有字段使用 snake_case。平台 ID、ASIN、SKU、订单号均按 STRING 读取，禁止先转数字再转回字符串。原始文件按字节归档，源表头和源值不因标准字段改名而变化。


| 旧名称／曾用名称                                            | v1.1 唯一名称／处理                                                                |
| --------------------------------------------------- | --------------------------------------------------------------------------- |
| country、marketplace_country、marketplace_code（表示国家时） | country_code：平台市场 ISO 国家代码，GB 表示英国；不是买家国籍                                   |
| brand、brand_id、internal_brand_id                    | brand_key：沿用公司稳定品牌键；显示名为 brand_name                                         |
| spu、sku                                             | internal_spu、internal_sku                                                   |
| product_category、category                           | 映射到 category_l1/2/3；层级未知时不猜测                                                |
| shade、size                                          | shade_name、size_or_volume                                                   |
| review_created_at、review_date                       | 按源精度映射到 review_created_at_utc / review_created_at_local / review_date_local |
| rating                                              | rating_normalized_5；保留 rating_raw、rating_numeric、rating_scale_min/max       |
| review_text_clean、review_text_cn、review_text_en     | review_text_cleaned、review_text_translated_cn、review_text_translated_en     |
| raw_payload_json                                    | raw_payload                                                                 |
| helpful_count                                       | helpful_vote_count                                                          |
| sha256                                              | sha256_hash                                                                 |
| mapping_failed_rows、unmapped_product_rows           | unmapped_rows；映射冲突另用 mapping_conflict_rows                                  |
| media_archived、media_download_status                | media_archive_status：在 current/serving 视图计算；不存冗余 BOOL                       |
| is_current_version                                  | current 视图派生；历史事实表不维护易漂移的冗余标志                                               |
| edited（review_status）                               | 编辑属于版本变化；评论可见状态统一为 active/hidden/deleted/unknown                            |
| reviewer_name、reviewer_id、reviewer_profile_url      | 默认只留受限 Raw；标准层仅可选 reviewer_alias_masked、reviewer_key_hmac                   |


兼容只发生在适配器输入层。DDL、API、SQL 和新配置不同时保留旧新两套字段。收到同一含义的多个源列时必须核对一致性，冲突进入异常队列。schema_version=v1.1；parser_version、template_version、identity_rule_version、rating_rule_version、mapping_version_id 各自独立。

`review_import_batch` 在 Firestore 控制库中维护即时状态、幂等凭据和租约，BigQuery 表是批次汇总投影。异步消息或任务状态不得靠 BigQuery 高频逐行 UPDATE 维持。Firestore 计划使用 Native / us-central1，尚未创建。

问题审核、案件修改、访问名单与删除请求也以控制库事务为准，审计事件批量同步 review_control；BigQuery 负责分析和可追溯快照。阶段二增加 review_semantic 下的 analysis_run、fact_review_segment、fact_review_issue、dim_issue_taxonomy，并将案件/人工审核事件投影到 review_control。详细 AI 字段在第 12 节定义。

## 3. 字段约束通则

R=该表每行必填，N=允许 NULL，C=满足说明中的条件时必填；数组无元素时为空数组。业务约束由 importer 和发布质量检查执行，不依赖 BigQuery 自动保证主外键唯一性。

- 评论正文、标题、用户昵称、订单号都可空；只有星级的评论也可入 Core。
- 内部 SPU、SKU、中文名可空；缺映射时保留 Core，product_mapping_status=pending，不伪造 SKU 或名称。mapping_status 仅用于映射表自身。
- 最小有效评论要求：可验证的平台/市场/来源作用域、至少一个可用平台商品别名、合法评分、可解析的评论日期。异常源行仍完整进入 Raw，并进入质量隔离队列。
- `source_timezone` 是 IANA 时区，由模板/可信源配置提供。源只有日期时 date_precision=date，UTC/本地时间戳允许 NULL；禁止编造 00:00:00 来表示精确发布时间。
- 星级默认只支持已验证的 1～5 星模板；1～2 星沿用低星定义，3 星单列。其他量表必须有明确转换配置；不对点赞、推荐/不推荐盲目线性换算。
- 布尔值未知为 NULL；例如没有“验证购买”字段不等于 verified_purchase=false。
- `review_date_local` 用于市场本地日趋势；跨市场按“各市场本地日期标签汇总”展示，不能称为同一 UTC 时间窗口。

## 6. fact_review：内容版本表

每行是一个确认的评论内容版本；原文与其版本一经发布不被清洗、翻译或商品映射修正覆盖。原文按批准保留期保存，合法删除是受审计的例外。

## 9. 评论身份、幂等和版本算法



### 9.1 身份作用域

```text
review_id = SHA256(canonical JSON [identity_rule_version, identity_namespace, source_review_id])
```

canonical JSON 使用 UTF-8、固定字段顺序/类型、明确 NULL、无歧义编码；禁止简单拼接字符串。

- 验证为公开目录的 Amazon 评论：namespace=平台 + 原生评论系统 + 原始市场；不含抓取它的店铺、上传人或可变品牌，避免跨店重复导出后多算。展示页市场与原始评论市场不同时以明确来源为准，未知不跨市场合并。
- 店铺型来源：namespace=平台 + 评论系统/应用 + market + store_id；Shopify 应用 ID 与店铺共同限定原生 ID。
- 尚未确认平台 ID 唯一范围：namespace 至少保留 source_scope_id，并标记 fallback；不能把经验假设当平台保证。

完整 source_scope_id、store_id、批次与权限仍保存在 observation，多来源命中同一 review_id 不丢血缘。访问权检查根据已批准来源与产品归属，不只依赖 fact_review 的首次来源。

### 9.2 没有原生 ID

fingerprint_v1 使用 namespace、可用平台商品键、源日期精度、评分、保守空白规范化正文/标题、可选 reviewer_key_hmac 和稳定媒体键生成候选。相同文件重传保证幂等；跨文件相同指纹是候选重复。

同一文件多条匿名同文同星同日记录、或候选匹配多个评论时，不能静默合并：保留每个 Raw，标记 identity_confidence=ambiguous，进入复核；无可验证证据时不保证跨文件唯一性，也不宣称能识别编辑版本。歧义观察可暂用 raw_id 生成 unresolved_observation ID，默认不参与已去重产品指标。

### 9.3 内容版本与旧文件重放

1. content_hash 覆盖原始标题/正文、评分及稳定媒体键；票数、下载状态、临时 URL 签名和导入批次变化不触发新评论版本。
2. 相同原生身份且内容与当前版本相同：新增 observation，不增评论版本。仅与历史版本相同的内容仍须先判断源时间；不能单凭历史 Hash 命中拒绝真实回改。
3. 内容改变且有可靠的新旧时间：同一 review_id 下产生新版本；若明确为较旧快照，只登记历史观察，不把 current 指回旧内容。
4. 无可靠源时间且内容冲突：version_order_status=pending_review，保留 Raw/observation 和冲突记录，确认后再发布；人工裁决留事件，不能用“上传更晚”断定“内容更新”。
5. 当前版本由已确认的 version order 和删除屏蔽事件生成 v_review_current；“A→B→A”的真实回改可产生新版本，但重放旧文件不会回滚当前版本。
6. 商品补映射、翻译、模型重跑不改变 review_version；分别使用 mapping_publication_id、analysis_run_id。
7. 后续导出缺少某评论只记录批次覆盖差异，不生成不存在的 Raw 行，也不改变评论状态。review_status=deleted 需要源明确状态或人工验证证据，不能由不完整导出推断。

`review_source_observation` 字段：observation_id STRING R、raw_id STRING R、import_batch_id STRING R、review_id STRING R、review_version_id STRING N、source_scope_id STRING R、source_snapshot_at TIMESTAMP N、observed_at TIMESTAMP R、ingested_at TIMESTAMP R、observation_time_basis STRING R、observed_content_hash STRING R、version_order_status STRING R（confirmed/historical/pending_review）、source_review_status STRING N、helpful_vote_count INT64 N、seller_reply_text STRING N、seller_reply_at TIMESTAMP N、status_evidence_ref STRING N。未确认内容可不绑定 review_version_id。逻辑评论 first_seen_at/last_seen_at 按 observation.ingested_at 的首次/最近入库计算；源事件顺序仍依据 observed_at 及其可信依据，二者不可混用。

## 11. 发布、分区、保留和迁移

- Raw 按 DATE(ingested_at) 分区，聚簇 import_batch_id、platform、source_scope_id；保留所有解析成功的源行与错误状态。
- fact_review 按 review_date_local 分区，聚簇 brand_key、internal_spu、platform、review_id。
- fact_review_media 按 review_date_local 分区，聚簇 review_id、review_version_id、download_status。
- observation 按 DATE(observed_at) 分区，聚簇 review_id、import_batch_id、source_scope_id。
- batch/error 按 DATE(uploaded_at)/DATE(created_at) 分区；映射表首期较小不分区，聚簇 product_scope_id、alias_type、alias_value、brand_key。每表最多四个聚簇列。
- staging 批量载入后校验，再发布；首期全流水线一个 Firestore 事务租约和递增 fencing token。Cloud Run task parallelism=1 不能阻止两个独立执行同时写。仅在提交前检查 Firestore 租约仍有竞态，必须同时使用下述 BQ 发布门记录。
- `import_publication_gate` 字段：pipeline_id STRING R、fencing_token INT64 R、commit_sequence INT64 R、last_publication_id STRING N、updated_at TIMESTAMP R；初始化且验唯一后只由协调器维护。新租约持有者先把 BQ gate 单调推进到其 token；每次合并必须在同一 BQ 事务中 ASSERT token 相等、UPDATE gate 的提交序号并断言恰好一行、再修改事实/发布清单。并发变更 gate 的事务若冲突则中止重读；旧 token 不能再次提交。回放/映射更正同样经过这个门。
- BQ 合并发布使用确定性 Job ID 和发布清单；Cloud Run 超时后先查询原 Job 结果再重试。Firestore 完成状态晚于 BQ 提交，恢复任务按 publication_id 对账。
- 首期每批最多 50,000 行；5,000 行只是 staging 装载分块，合格内容在一个 BQ 事务中发布。`review_control.import_publication`：publication_id STRING R、import_batch_id STRING R、fencing_token INT64 R、commit_sequence INT64 R、bq_job_id STRING R、schema_version STRING R、published_at TIMESTAMP R；与事实在同一事务提交。媒体后续归档不重做该次内容发布。
- 控制库 `review_identity_registry`：review_id STRING R、identity_namespace STRING R、known_review_dates ARRAY R、current_review_version_id STRING N、last_publication_id STRING R、registry_revision INT64 R、updated_at TIMESTAMP R；只作为历史分区定位索引，不是第二套事实源。BQ 已提交而索引未同步时，后续写者先按发布清单补齐；索引缺失/过期必须执行受预算控制的历史查找或暂停，不能当作新评论直接插入。已批准删除同时清理或按政策最小化该索引。
- Raw/Core/媒体的有效保留期由 retention_policy_id 引用，不再承诺永久保存。到期和已批准删除要覆盖源文件、BQ 所有版本、媒体 generation、安全副本、导出、缓存、Embedding、分析和可识别内容审计；备份/软删除剩余周期另计，不能承诺点击后全介质即时物理消失。
- 若一份文件含其他需保留记录，先按批准规则生成其余数据的受限替代文件，再处理旧对象及保留窗口；删除清单只保留最小非内容证明。源文件“不覆盖”原则不阻止受审计的删除流程。
- 现有 VOC 项目尚无表迁移事实；新建按本文。若实施时已有旧表，先建兼容视图和 staging，验证行数/唯一键/回滚后再迁移，不直接覆盖历史。

控制库 `data_asset_policy` 登记资产与保留关系：asset_id STRING R、asset_type STRING R（source_file/raw_row/review_version/media/export/analysis）、asset_reference STRING R、source_scope_id STRING R、retention_policy_id STRING C（生产数据启用前必填）、expires_at TIMESTAMP N、legal_hold BOOL R、erasure_status STRING R（none/requested/approved/erasing/logically_hidden/physically_expired）、policy_revision INT64 R、updated_at TIMESTAMP R。源文件与所有派生资产按 observation/media/analysis 关联建索引；未批准具体期限不能凭 NULL 解释为永久。

## 13. 必须由人工补充的事实

1. 运营提供真实原始导出和导出方法/筛选范围；Codex 据此完成模板和异常样本。先给一个可取得原文的来源即可，其他平台随后。
2. 产品主数据负责人确认缺失 SPU/SKU、父子粒度和冲突映射；Codex 复用现有数据并生成待补清单。
3. 业务/数据负责人确认允许处理的来源、市场、媒体和保留期限；US 区域已由用户确定，新增市场是否适用不能由工程设计代替判断。
4. 用户提供实际访问人员及品牌/市场/导出权限；IT 完成域名、登录配置和部署验收。秘密值直接进入 Secret Manager。
5. 订单强度或 AI 阶段再确认销售分母合同、业务问题字典和标注责任人；这些不阻塞阶段一的技术开发。
